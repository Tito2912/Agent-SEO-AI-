# Noyaru en plusieurs langues

Noyaru s'écrit en français. L'anglais est une **traduction** : aucun gabarit n'est dupliqué,
aucun texte français n'est remplacé par une clé technique.

## Le principe : la clé est le texte français

```jinja
<h1>{{ tr("Comprenez votre SEO.") }}</h1>
```

- En français, `tr()` affiche le texte tel quel.
- En anglais, `tr()` cherche ce texte dans `locales/en.json` :
  `"Comprenez votre SEO.": "Understand your SEO."`
- **Texte absent du catalogue → il s'affiche en français.** Un écran pas encore traduit reste
  utilisable ; il n'affiche jamais une clé ou un blanc.

Le gabarit se lit donc toujours en français, comme avant.

## Les cas courants

| Besoin | Écriture |
| --- | --- |
| Texte simple | `{{ tr("Se connecter") }}` |
| Texte avec une valeur | `{{ tr("{n} pages analysées par mois", n=gratuit.pages) }}` |
| Texte qui contient un lien ou du gras | `{{ tr_html('Consultez le <a href="{url}">comparatif</a>.', url=lien) }}` — les valeurs sont échappées |
| Texte venu du serveur (`msg`, `err`, libellés de la grille des plans) | `{{ tr(err) }}` — traduit s'il est au catalogue, sinon affiché tel quel |
| Message `error` d'une réponse JSON | rien à faire : `app.py` et `cms_routes.py` utilisent `i18n.JSONResponse`, qui le traduit par le catalogue dans la langue du client |
| Texte d'un e-mail ou d'un module Python | `i18n.tr_current("Bonjour,")` (voir `_mail_tr` dans `app.py`) |
| Langue de la page | `<html lang="{{ current_lang() }}">` |
| Sélecteur de langue | `{% include "_lang_switch.html" %}` (ou `{% with compact = true %}…{% endwith %}`) |

**Les nombres calculés** (« 12 sites suivis », « 20 000 pages analysées/mois ») se traduisent
sans rien changer au code Python : le catalogue les connaît sous la forme
`"{0} sites suivis": "{0} tracked sites"`. Les nombres reprennent leur place, au format anglais
(`20,000`).

## Choix de la langue

1. l'adresse d'une page publique (`/en/pricing`), ou `?lang=en` dans l'adresse (c'est ce que
   fait le sélecteur sur les autres pages), mémorisé ensuite dans le cookie `noyaru_lang`
   pendant un an ;
2. le cookie `noyaru_lang` ;
3. la langue d'affichage choisie dans « Mon compte » (préférences) : elle suit le client sur
   tous ses appareils, et l'enregistrer met aussi à jour le cookie du navigateur ;
4. la langue du navigateur (`Accept-Language`) : français → français, anglais → anglais, une
   autre langue seulement (allemand, espagnol…) → anglais ;
5. sinon, le français. Un robot d'indexation n'envoie en général ni cookie ni langue : il voit
   la version française, la version de référence.

## Adresses par langue des pages publiques

L'accueil, les tarifs, le support et le statut (`LOCALIZED_PAGES` dans `backend/i18n.py`) ont
une adresse par langue, que Google indexe séparément :

| Français (par défaut) | Anglais |
| --- | --- |
| `/` | `/en/` (`/en` y renvoie) |
| `/pricing` | `/en/pricing` |
| `/support` | `/en/support` |
| `/status` | `/en/status` |
| `/docs` | `/en/docs` |
| `/docs/<page>` | `/en/docs/<page>` (si la page est traduite) |
| `/ressources-seo` | `/en/ressources-seo` |
| `/ressources-seo/<guide>` | `/en/ressources-seo/<guide>` (si le guide est traduit) |
| `/terms`, `/privacy`, `/mentions-legales` | `/en/terms`, `/en/privacy`, `/en/mentions-legales` |

- `i18n.LocalizedPaths`, déclaré en dernier dans `app.py` (donc exécuté en premier), sert
  `/en/pricing` par la route de `/pricing` en fixant l'anglais. Les contrôles d'accès et les
  routes ne voient que l'adresse française : aucune route n'est dupliquée.
- Chaque page annonce ses versions (`<link rel="alternate" hreflang="fr|en|x-default">`, dans
  `public_layout.html`) ; son adresse canonique et `og:url` sont celles de sa langue ; le plan du
  site (`/sitemap.xml`) liste les deux versions.
- Sur une page en anglais, les liens publics (`campaign_link`) mènent aux adresses anglaises, et
  le sélecteur renvoie vers l'adresse française avec `?lang=fr` (qui remplace le choix anglais
  mémorisé). Une personne connectée garde des adresses simples : sa langue suit son compte.
- Ajouter une page : l'ajouter à `LOCALIZED_PAGES` ; sa route et son gabarit ne changent pas,
  mais son adresse canonique doit passer par `localized_path(...)`.

## Ajouter ou modifier un texte traduit

1. Entourer le texte de `tr()` dans le gabarit.
2. Ajouter la ligne dans `locales/en.json` (texte français exact → texte anglais).
3. Lancer `python -m pytest seo-agent-web/tests/test_i18n.py`.
   Le test échoue si un texte entouré de `tr()` n'a pas de traduction anglaise, ou si une
   traduction perd une variable `{…}`.

Modifier un texte français entouré de `tr()` change sa clé : penser à mettre à jour la ligne
correspondante de `locales/en.json` (sinon le test le signale).

## Ajouter une langue

1. Créer `locales/<code>.json` (même format que `en.json`) et, pour le formulaire,
   `locales/countries_<code>.json`.
2. Ajouter la langue à `LANGUAGES` dans `backend/i18n.py`.

  les deux sens (`content_library._localize_links`).
- `TRANSLATION_DIRS` dans `content_library.py` réunit les dossiers traduits des deux
  collections ; `blog_pages(lang)`, `get_article(slug, lang)`, `featured_articles(n, lang)`.
- L'accueil anglais met en avant les guides anglais. `tests/test_i18n_guides.py`.

**Pages juridiques**
- Une version anglaise écrite à part (`terms_public_en.html`, `privacy_public_en.html`,
  `legal_notice_public_en.html`), pour être relue comme un document entier, et non par phrases du
  catalogue. La route choisit le gabarit selon la langue (`_legal_page` dans `app.py`).
- L'éditeur, le médiateur, l'hébergeur et les dates viennent de `backend/legal.py`, commun aux deux
  langues. Modifier une clause : la modifier dans les deux gabarits, dans le même changement ;
  `tests/test_les_pages_juridiques_sont_bilingues.py` vérifie que les deux versions gardent les
  mêmes articles. Détail et validations : `docs/legal/`.

**Phrases composées par le code avec une valeur du site** (« … la marque (exemple.fr) … ») : le
catalogue les connaît avec un trou nommé, `"… la marque ({domain}) …"`. Seuls les noms
`{domain}`, `{url}`, `{src}`, `{label}`, `{candidates}` et `{detail}` (le second trou d'une
phrase à deux valeurs) ouvrent un trou dans une phrase libre ; la valeur insérée est elle-même
traduite si elle figure au catalogue. Le test
`test_every_issue_explanation_has_an_english_translation` signale toute explication modifiée dont
la traduction manque.

Textes dans du JavaScript :
- dans un `<script>` d'un gabarit : `{{ tr("…")|tojson }}` ; une phrase avec une valeur garde
  son trou nommé et se remplit dans le script : `fill({{ tr("{n} versions rédigées.")|tojson }}, {n: total})`
  (`content.html`, `competitors.html`) ;
- dans un fichier `static/*.js` : `noyaruT("texte français")`. Au démarrage, Noyaru repère ces
  appels dans `static/*.js` et n'envoie à la page que leurs traductions
  (`templates/_lang_script.html`). Ajouter la ligne correspondante dans `locales/en.json` ; le
  test `test_static_scripts_receive_only_their_translations` signale un oubli. En début de
  fichier : `const noyaruT = window.noyaruT || ((text) => text);`.
